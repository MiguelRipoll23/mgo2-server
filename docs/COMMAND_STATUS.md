# Command status — every lobby command id, for this server

The same tables as [`PACKETS.md`](PACKETS.md), with the `our status` column
recalculated for **this** repository.
`PACKETS.md` is the reference server's own packet reference, kept here verbatim:
its status column describes that server, not ours, and its `served` therefore means
"the reference answers this", which is a different claim from "we do".

Generated by `tools/command_status_report.py`. Regenerate it after changing a
registration in `src/*/Commands/*CommandHandlerRegistration.cs` or adding a reply id,
or the column and the code part company.

* **served** — the command the client sends is answered, or a reply the client parses
  is emitted.
* **gap** — the client sends it and we do not implement it. A reachable stall.
* **unsent** — the client can parse it and we never emit it. Benign unless a screen
  waits on the reply.
* **PHANTOM** — we emit an id the client has no parser for. A defect, not tidiness.
* **MISNUMBERED** — we answer a neighbouring id instead of the real one. A defect.

The last two have **no row in the tables at all**, which is what makes them defects
rather than gaps: the client neither sends nor parses those ids, so neither id list
the tables are built from contains them. They are listed under *Ids we touch that the
client does not* instead.

The reference also writes `handled` and `sent` on four rows (`0x43A4`/`0x43A5` and
`0x43C4`/`0x43C5`). Those spell the same two states differently, so this table uses
`served` for all four; the rows are called out in the counts above only so the two
files can be reconciled row for row.

## How the column was derived

* **answered** — 85 ids, read from the `registry.Register` calls. The
  registry is the inventory of what a client can get an answer from, so a command that
  is only special-cased in the socket loop is invisible to it. `0x0003` and `0x0005`
  used to be exactly that; they are registered commands now.
* **emitted** — 122 ids: command constants this source references and does
  not register, plus the ids the older handlers pass as bare literals. A reply id that
  is only *defined* is `unsent`, which is what the column means here.
* **client direction** — the ELF id lists in the reference's `dev/analysis/`, the same
  source its own tables cite. An id in neither list is an id the client neither sends
  nor parses, which is what the two defect labels are for.

**What this cannot tell you.** It is a reading of source, not of a client: `served`
means a handler exists, not that the client accepted the reply — the reference's own
caveat for its column applies here unchanged.

## Evidence from the deployment

Checked against the server running on `raspberrypi` on 2026-09-16 (every `mgo2-*`
container, ~517k log lines, the whole window the containers retain):

* **Inbound opcodes actually observed: 16**, and every one is answered —
  `0x0003`, `0x0005`, `0x2005`, `0x2008`, `0x3003`, `0x3048`, `0x3103`, `0x4100`,
  `0x4130`, `0x4150`, `0x4300`, `0x43D0`, `0x4700`, `0x4820`, `0x4900`, `0x4990`.
* **Zero `no-handler` lines and zero handler failures.** No command a client sent ever
  went unanswered, which is the only claim about coverage the logs can support.
* **None of the eleven ids dropped from the registry appeared inbound.** Five of them
  (`0x4122`, `0x4124`, `0x4125`, `0x4140`, `0x4142`) appear only outbound, as the
  connect burst's pushes, which is why the pushes were kept and the handlers were not.
* `0x0003` (13×) and `0x0005` (9×) both appeared inbound, which is what makes them
  commands rather than socket plumbing.

The window is hours long, not months, so read this as "no counter-example", not proof.
The static reading above is what carries the claim for ids nobody has exercised yet.

## Command-count parity

* This server answers **85** request ids; the reference answers **84**
  (83 of them in the ELF client-to-server list, plus the `0x0001` handshake echo).
* **Every command the reference answers is answered here.** The difference is
  `0x4348`, which the client sends (`0xd4a8a4`) and the reference leaves as a `gap`;
  keeping it is a deliberate choice — matching the reference exactly would mean
  removing the answer to a command the client genuinely issues.
* The eleven ids this pass removed from the registry were the ones the client never
  sends; see the deployment evidence above.

## Open items

1. **The `0x4101` grid length** is still disputed: this server sends a `0x229` grid
   with 64-id friend and blocked arrays and a content mask at `0x22a`, the reference
   sends `0x142` with 32-id arrays and no mask. Both cite a parser address. The test is
   a live client with a deliberately narrowed mask: if narrowing it changes the
   create-game rows, the mask is read. See `command-handler-comparison.md` §7.
2. **The three phantoms** above, each for the reason recorded with it.
3. **`0x4900`'s entry length** is a fixed 35 bytes here and sized per client build on
   the reference (64 bytes of text on 1.0, none on 1.36). 35 is the 1.36 layout, which
   is the build this server targets, so there is nothing to size until a 1.0 deployment
   is wanted — at which point the length belongs in the configuration next to the other
   build-specific values.
4. **Not verified against a client**: the ranking boards' `skey` meanings, and the
   combat-training graduation flow end to end.
